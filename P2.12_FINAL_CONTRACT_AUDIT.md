# P2.12 FINAL CONTRACT AUDIT

Second audit after implementation, against the reconciled contract. Sources:
working-tree delta (new `src/daemon/` 16 modules / 3534 lines +
`cli/commands/daemon.ts` 350 + 2 new test files, plus 5 modified files),
focused suites (62 + 16 + writer/architecture/boundary batches), full watchdog
run (4297 pass / 23 skip / 7 fail / 4327 tests / 294 files), `tsc` (28 = the
baseline set, 33 output lines), targeted biome on the touched set (0 errors),
repo-wide lint versus a pristine-HEAD worktree measurement (457 vs 554), and
a cross-process CLI smoke of the whole start→status→issue→sessions→stop
cycle.

## Is P2.12 architecture still consistent with the reconciled contract?

Yes. The daemon is a host, not a new runtime: hosted sessions are the same
durable session objects living in another process; presentation/snapshot
identity remains `(session_id, event_seq)`; the daemon reads the store through
the schema owner (`persistence.ts`) and appends nothing it is not authorized to
append. The handshake order, non-atomic snapshot, `tail|resume|number`
subscription semantics, discovery/lease rules, control idempotency, and
approval state machine are implemented as specified and pinned by tests.

## Did implementation introduce any second authority or a second event system?

No. `src/daemon` has no second store schema (its two tables are declared in
the single schema owner), no own event bus (feed/subscriptions wrap the
existing presentation stream), and no writer role — append authority stays
with the writer epoch fence. A guard asserts there is no
`INSERT INTO presentation_events|messages|semantic_events` in the daemon and
no value-level re-import of presentation events; another asserts the literal
`adopt(` is absent. Telemetry counters are excluded from every decision file.

## Can recency be mistaken for liveness, or a PID become authority?

No. `.minicode/daemon-endpoint.json` with a fresh lease is only a candidate;
`alive` is reported exclusively by a successful probe (only `probeDaemon` may
set it). Discovery code reads neither PID nor lease age as a decision input —
both are asserted by guard and exercised by the discovery suite.

## Can UNKNOWN become success, or a decision be reversed?

No. The approval machine's terminal states are non-reversible (guard), expiry
and storage failure are reported as deny rather than as success, and a row
still `pending` after a restart resolves to `UNKNOWN`, never to an inferred
decision. Approval UI remains proposal-only: authority lives in the
scope-checked `approval.decide` path.

## Can an unauthorized consumer attach, or credentials cross IPC?

No. Every control operation carries an explicit minimum scope (guard-enforced
map of all eight ops); `admin` is not a wildcard; capability verification
anchors in the endpoint's bootstrap trust root; `protocol.ts` contains no
credential, writer token, or bootstrap secret (guard). Refusals are explicit
codes, and a consumer without `subscribe` is rejected at handshake rather than
served an empty feed.

## Can offsets regress or a queue grow without bound?

No. Consumer offsets are monotonic and acks never pass the cursor (guard);
the per-connection queue is bounded with explicit refusals; offsets are stored
workspace-locally via `openWorkspaceSessionDb`, which cannot fall back to the
global `~/.minicode` (this fallback was a real bug found and fixed: daemon
rows were landing in the global DB).

## Can a child be adopted, or reported complete without reporting?

No. `children.ts` supervises only children of the current generation (guard:
no `adopt(`), completion requires a report, and children inherit no approval
authority.

## Can the shutdown path lose its own confirmation?

It could, and was fixed: `daemon.shutdown` defers execution one event-loop
turn and socket teardown flushes (`end()` + delayed destroy) before closing,
so `control_result` reaches the operator. Verified end-to-end across processes
(`stop` → exit 0, endpoint removed, process gone, `status` → 3 afterwards).

## Do the frozen boundary tests still hold?

Yes. `test/ui-boundary.test.ts`, `test/import-convention.test.ts`,
`test/architecture-map.test.ts`, `test/p2-architecture-guards.test.ts`, and
`test/writer-inventory.test.ts` all pass with the daemon included: `src/daemon`
imports neither `cli/` nor `src/ui/`, the composition root stays in
`cli/commands/daemon.ts`, `docs/ARCHITECTURE.html` carries all 16 modules in
four new blocks (group count 19), and the CLI writer inventory stays at its
declared owner entry (6 writers, `human-cmd`, declared rather than absorbed).

## Did any later-phase work enter P2.12?

No. No P2.13 surface, no Desktop UI screen, no second persistence layer, no
global event ID, no auto-re-execute/auto-accept path. `vendor/minicore` is
untouched (`git status --porcelain -- vendor/` empty, guard-enforced) and no
`#minicore` contract changed.

## Was the baseline respected?

Yes. `tsc` is byte-identical to the baseline set (28 errors, all in untouched
`test/phase3*`/`phase4*`). Repo lint is 457 errors versus 554 measured on a
pristine checkout of HEAD — strictly better, with all 22 error-bearing files
pre-existing and none of them a P2.12 file (touched-set biome: 0 errors). All
7 full-suite failures are the already-qualified set (2 pre-existing baseline,
5 session-identity flakes); coverage refuses evaluation on that same set and
pack keeps its 2 pre-existing failures. No new regression, no test weakened.
