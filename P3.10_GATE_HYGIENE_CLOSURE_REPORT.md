Klasifikasi setiap failure dengan bukti:

### 3.1 m15 P3 — STALE GUARD (guard terlalu tajam, bukan kode berbahaya)

- **Root cause**: `test/m15-production-integration.test.ts` menggunakan pathspec git
  `git ls-files "src/**/*.ts" "cli/**/*.ts" "test/**/*.ts"`. Pathspec `src/**/*.ts`
  **tidak cocok untuk berkas datar** — `git ls-files "src/**/*.ts"` mengembalikan **0
  berkas datar** (blind spot terukur). Akibatnya separuh berkas produksi tak pernah
  dipindai, termasuk `src/config.ts` yang di-P3.10 Phase 2 divalidasi sebagai lokasi
  yang memungkinkan constructor `createRecoveryEngine()` berdiri sendiri.
- **Fakta produksi**: perubahan yang dilakukan di sesi ini **bukan** whitelist — tapi
  refactor kepemilikan: `dispatch.ts` sekarang impor predikat murni `isPlanCurrent` dari
  `recovery.ts`, dan `createRecoveryEngine` tetap di `recovery.ts` + composition root
  saja. `isPlanCurrent` adalah fungsi murni (nol state, nol efek), jadi M13 bisa bergantung
  pada M12 tanpa memegang authority. Guard diperkuat (jika tidak diperbaiki pathspec, ia
  akan tetap buta terhadap `src/config.ts`).
- **Bukan**: whitelist `dispatch.ts`. Guard tetap menolak constructor authority di luar
  lokasi yang diizinkan; yang diubah adalah **daerah gim yang dipindai** dan **cara M13
  bergantung pada M12**.

### 3.2 S13 — TEST BUG (CRLF checkout Windows)

- **Root cause**: `test/runtime-shutdown.test.ts` membaca `cli/setup.ts` mentah dan mencari
  posisi string `"\n    detachUI()\n"`. Di checkout Windows (`core.autocrlf`), berkas
  tersimpan CRLF, sehingga `indexOf` = -1 meskipun urutan benar.
- **Invariant yang diuji**: URUTAN, bukan encoding baris. Fix = normalizer EOL baca
  `.replace(/\r\n?/g, "\n")` dengan komentar eksplisit. Tidak mengubah production behavior.
- **Bukti**: tanpa normalizer, test gagal di checkout CRLF; dengan normalizer, test hijau di
  checkout apa pun (LF maupun CRLF).

### 3.3 web-ssg — TEST BUG + 1 REAL FIX (dokumentasi)

- **Root cause guard**: guard mendeteksi baris `^\s+[-*] ` di semua berkas `docs/*.md`.
  Ternyata 2 dari 3 offender adalah **false positive** dari dalam blok kode fenced
  (``` / ~~~) — contoh JSDoc yang menggunakan baris ` *  teks`. Guard harus skip fence.
- **Real offender**: 1 nested list nyata di `docs/TASK_EVENT_MODEL.md` (baris ~143,
  `  - planId …` + continuation). Fix = 2 langkah: (a) guard skip fenced blocks; (b) nested
  list nyata direflow menjadi flat (komas + baris baru, bukan indentasi).
- **Tidak**: weaken validator. Validator tetap menangkap nested list nyata; hanya false
  positive fence yang hilang.

### 3.4 §28 — TIMING FLAKE (timeout runner bawaan bun)

- **Root cause**: `test/phase6v-adversarial-audit.test.ts` §28.1 assertion sendiri menulis
  kontrak temporal `ms < 60_000`, tetapi bun default timeout **5 detik** membunuh test
  sebelum assertion terkumpul.
- **Temuan**: 10 run terisolasi: 4,53–5,38 dtk (median 4,88), 3 run gagal murni karena
  melewati 5 detik — bukan drift/wedge. 500 iterasi memang berat (tiap `fire` menjalankan

- **Fix yang dipilih**: timeout eksplisit **70_000 ms** (di atas pagu 60 dtk agar kegagalan
  yang berarti tetap dilaporkan oleh assertion kontrak, bukan oleh timeout runner). Bukan
  retry, bukan sleep. **Bukan masking**: test tetap memberi tahu jika ekssekusi nyata
  melebihi 60 detik.

## 4. m15 Analysis

### 4.1 Pertanyaan arsitektural: apakah dispatch.ts menciptakan second authority?

**Jawaban pendek**: TIDAK. dispatch.ts adalah **bridge terjemahan** (WHAT/WHEN → CAN/HOW),
bukan owner authority. Ia tidak memiliki lifecycle sendiri, tidak menyimpan state mutable
yang menjadi sumber kebenaran, dan tidak menulis canonical state.

**Detail kepemilikan**:

| Simbol | Owner konseptual | Lokasi sah | Peran |
| --- | --- | --- | --- |
| `createRecoveryEngine` | M12 (recovery) | `src/runtime/recovery.ts` + composition root | Engine dengan state mutable (cache idempotensi + counter) + metrics; lifecycle milik composition root |
| `isPlanCurrent` | M12 (recovery), ekspor murni | `src/runtime/recovery.ts` | Predikat freshness plan M12 — nol state, nol efek |
| `dispatch.ts` | M13 (dispatch bridge) | `src/runtime/dispatch.ts` | Bridge: validasi authority/budget/deadline/capability/parent-child, revalidasi plan M12, dedupe dispatch-id, teruskan SATU request ke AdmissionPort |

### 4.2 Apakah instance RecoveryEngine di dispatch.ts adalah second authority?

**Sebelum fix**: `src/runtime/dispatch.ts:35` punya `const planValidator = createRecoveryEngine()`
di module-scope. `RecoveryEngine` memegang mutable cache + metrics dan **tidak punya shutdown
latch** → instance di scope modul bridge = authority kedua yang tak pernah di-shutdown
bersama composition root. Inilah yang dilarang guard m15 P3.

**Setelah fix**: dispatch.ts tidak lagi membuat instance engine. Ia mengimpor predikat murni
`isPlanCurrent` dari `recovery.ts` dan hanya menggunakannya sebagai validator pada admission.
Kepemilikan M12 tetap di `recovery.ts`; M13 hanya **bergantung pada M12** melalui predikat,
bukan membuat instance.

```bash
# Bukti operasional: dispatch.ts tidak lagi impor createRecoveryEngine
grep -n "createRecoveryEngine\|isPlanCurrent" src/runtime/dispatch.ts
# → hanya isPlanCurrent yang diimpor (createRecoveryEngine tidak ada di dispatch.ts)
```

## 5. S13 Analysis

### 5.1 Apa yang harus terjadi sebelum runtime boleh dianggap terminal?

Urutan teardown yang diuji oleh S13 adalah urutan di `cli/setup.ts` composition root:

```text
1. productionScheduler.stop("shutdown")        # hentikan future scheduling + tunggu
   (baris ~2278)
2. productionRuntime.stop()                   # runtime latch + drain
   (baris ~2308)
3. detachUI()                                 # lepas display setelah runtime mati
   (baris ~2315)
```

Invariant: **scheduler harus berhenti sebelum runtime berhenti** — scheduler adalah penjadwal
aktivitas; runtime adalah mesin eksekusi. Jika runtime berhenti duluan, scheduler bisa masih
mencoba menjadwalkan / memicu aktivitas ke runtime yang sudah tak punya latch → behaviour
tak terdefinisi.

### 5.2 Apakah scheduler.stop() cukup sebagai sibuk?

`productionScheduler.stop("shutdown")` di `src/task/production-scheduler.ts` (lihat guard
m15 — lokasi yang di-scan): scheduler berhenti berarti tidak ada trigger/schedule baru yang
diperbarui; runtime kemudian bisa ditutup dengan aman.

### 5.3 Test bug vs invariant

Test S13 tidak menguji **isi** dari scheduler.stop(); ia menguji **posisi relatif** dari
panggilan `productionScheduler.stop("shutdown")` vs `productionRuntime.stop()` vs
`detachUI()` di `cli/setup.ts`. Invariant yang diuji adalah urutan, bukan implementasi
scheduler.

Test bug asli: pencarian posisi `indexOf("\n    detachUI()\n")` gagal di CRLF karena CR
di antara LF dan indentasi 4 spasi. Normalizer EOL memperbaiki ini tanpa mengubah invariant
yang diuji.

## 7. §28 Flake Analysis

### 7.1 Root cause

Test §28.1 menjalankan 500 iterasi `fire()` siklus scheduler nyata + SQLite. Assertion sendiri
mengklaim `ms < 60_000` (kontrak < 60 detik). Tetapi bun default timeout **5 detik** membunuh
test sebelum assertion terkumpul → test "gagal" bukan karena kontrak dilanggar, tapi karena
runner timeout.

### 7.2 Temuan terukur (10 run terisolasi sebelum fix)

```text
pass  : 7
fail  : 3
timing: 4,53–5,38 dtk (median 4,88)
penyebab gagal: hanya melewati 5 dtk runner bawaan bun
bukan: drift, wedge, growth, resource starvation, race
```

### 7.3 Keputusan fix

Dua opsi yang dipertimbangkan:

1. **Sleep / retry** — ditolak. Tidak ada synchronisasi actual condition; hanya menunda.
2. **Timeout eksplisit 70_000** — dipilih. Di atas pagu 60 dtk kontrak agar kegagalan yang
   berarti tetap dilaporkan oleh assertion (`ms < 60_000`), bukan oleh timeout runner.

Komitmen: **bukan masking flake**. Test tetap akan gagal jika eksekusi nyata benar-benar
melebihi 60 detik — hanya saja kegagalan itu akan disebabkan oleh kontrak temporal yang
dilanggar, bukan oleh runner yang tiba-tiba membunuh test di menit ke-5.

### 7.4 Bukti §28.1 hijau dalam suite penuh

Dalam run penuh 1307.22 detik ini, §28.1 menyelesaikan **5,29 detik** (log: `§28 long-run
stability > §28.1 500 trigger/cycle iterations: no drift, no growth, no wedge [5294.52ms]`).
Tanpa timeout eksplisit, 5 detik pertama bisa saja membunuh test di beban yang sama.

```bash

# → hijau (termasuk §28.1)
```

### 12.4 Keputusan threshold

**Tidak** menaikkan threshold 2.25 MiB unilateral. Alasan:

1. Threshold 2.25 MiB adalah sinyal bahwa paket tidak membawa sampah (node_modules, test, artifact).
   Di sini gate parts 1–6 semuanya PASS; hanya ukuran yang melebar. Artinya paket **tidak
   membawa sampah**, hanya payload legit yang besar.
2. Menaikkan threshold hanya agar `22/23 → 23/23` tanpa perubahan konten adalah arbitrary
   threshold relaxation — dilarang oleh prompt.
3. Keputusan untuk menaikkan threshold (jika ada) harus explicit ownership decision, bukan
   sekadar supaya gate hijau.

**Keputusan yang diambil**: tanda tangani sebagai "owner decision: threshold 2.25 MiB tetap;
isi sah; sisa failure adalah cek ukuran karena payload legit yang besar, bukan sampah. Apakah
threshold harus naik adalah keputusan pemilik, bukan bagian dari P3.10 closure."

Dokumentasi debt: threshold 2.25 MiB untuk payload ini cacat secara _konseptual_ — ukuran
paket yang sah bisa membesar karena dokumen/teks (bukan sampah), dan gate pack harus
membedakan "dibawa sampah" vs "dibawa payload legit besar". Rekomendasi owner: jika payload
ini diterima sebagai wajar, naikkan threshold ke nilai yang mencerminkan payload sah ini, atau
pisahkan cek ukuran menjadi "tidak ada sampah" vs "ukuran wajar" dengan threshold berbeda.
Sesi ini tidak memutuskan nilai baru.
