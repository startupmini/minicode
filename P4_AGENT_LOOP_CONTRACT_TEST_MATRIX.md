## 1. Purpose and audit method

For every requirement the matrix records the production file/function, the exact test file and test title, and whether that test exercises production code directly, a mock, or source text. A test is cited as evidence only after its title, body, and execution path were inspected; code presence alone is never treated as verified behavior, and a green suite is never treated as complete coverage. ## 4. Current Agent Loop execution-flow summary

Composition root `cli/setup.ts:626` `createCliSession` admits the session writer (`acquireSessionWriter`, `:678-680`), buries crash residue (`tombstoneDeadRuns`, `:700`; `tombstoneOrphanChildRuns`, `:704-711`), and returns the handle. A turn is driven by `runPromptWithVerify` (`:1739-1779`): pre-turn admission gate `ensureWriterFresh()` (`:738-758`, called `:1742`), `markPreviousRunTerminal()` (`:769-778`, called `:1747`), `createRun` + `transitionRun(RUNNING)` (`:1749-1750`), `markTurnActive` (`:1761-1766`), budget watcher + combined signal (`:1794-1817`), `session.run` via `executionRunner` (`:1826-1836`), outcome classification `classifyTurnError` (`:780-787`) recorded as `lastTurnOutcome` (`:1769-1772`), settle diagnostics (`:1837-1850`), and `finally { detachUI; clearTurnActive }` (`:1773-1778`). Kernel `executeTurn` (`vendor/minicore/src/core/loop.ts:27`) iterates model call, response interpretation, single-batch tool dispatch, and result pairing; per-turn `turnStore` commits only on success (`session.ts:220-232,245-248`). Host `persistCurrent` (`cli/setup.ts:2026-2114`) guards every durable mutation with writer epoch and finalizes the journal after durable history.

CLI (`cli/index.ts:456`), exec (`cli/commands/exec.ts:118`), ACP (default factory seam `cli/commands/acp.ts:352`, per-run session `:367`) all reach `createCliSession`. TUI (`cli/tui.ts:103` `runTui`) deliberately does not create a session; it drives the `CliSession` built upstream by `cli/index.ts:456` — turn loop `:312`, `persistCurrent` `:318`, close `:612/:616`. Daemon (`cli/commands/daemon.ts:218-219`) uses the same factory. Scheduler reaches the loop only through the injected `runTurn` seam (`src/task/autonomous-adapter.ts:130`); direction is one-way (Scheduler → session), never loop → scheduler.

## 5. Component ownership boundaries

- Kernel `executeTurn`: model-to-tool-to-observation iteration, provider sampling retry, context-length/budget compaction mechanics, `maxSteps` and per-step bounds. It retries provider sampling only; tool batches run once per step; it deliberately performs no side-effect deduplication.
- Host `runPromptWithVerify`: session admission, run lifecycle, budget watching, signal plumbing, verification/self-heal wrapper, presentation drain, and durable publication.
- Session layer: canonical-history authority (`saveSession`), writer-epoch fence, run state machine, guarded shrink, journal durability.
- Phase 3 (frozen): selector, projection producer/consumer, runtime metadata, fold renderer — the host consumes them; no Phase 4 row re-opens them.
- Tool Execution (`src/policy/executor.ts` + kernel executor): argument validation, dispatch, order/parallelism policy, error-to-result conversion.
- Task System / TaskGraph / Scheduler: task lifecycle, dependencies, readiness, scheduling. The loop→task boundary is exactly two edges: `todo_write/todo_read` → TaskStore (`src/tools/todo.ts`), and `delegate_task` → child session (`src/tools/task.ts`). No lifecycle/dependency/scheduling responsibility is duplicated inside the loop (verified by absence of those imports in `src/app/**` and `vendor/minicore/**`, and by structural guards below).
- Runtime admission (M13/M12): admission gate, recovery/redispatch planning, supervisory suppression. Retry safety and idempotency ownership live here, not in the loop.
